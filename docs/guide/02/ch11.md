# 第 11 章 给 AI 立规矩 · CLAUDE.md 与技能

AI 对你独有的约束一无所知，除非你告诉它。第一册第 12 章立下这条原则，这一章讲怎么把"告诉它"变成制度，省得每次开工重复一遍。

制度的载体是仓库根目录的一个文件，<strong>CLAUDE.md</strong>，项目的宪法，Claude 每次在这个项目里开工都会先读它。写什么？四节足矣。<strong>这是什么</strong>，项目一句话简介，技术栈四大件。<strong>怎么跑</strong>，怎么装依赖，怎么本地启动。<strong>规矩</strong>，代码风格，目录约定，"改动前先给计划"之类的流程要求。<strong>红线</strong>，哪些文件绝对不许碰，哪些操作必须人来确认。我们把链上合约相关的一切列在红线里，这就是那次"链上考古"的制度化答案。

比宪法更进一步的是<strong>技能（Skill）</strong>，可复用的专项规程。宪法管这个项目里的通则，技能管做某类事时的专门章程。我们已经在真用了，硬件那套接线与调试规程是一个技能，工程护栏是另一个。通则写进 CLAUDE.md，专门章程拆成技能，AI 遇到对应场景自动取用。

规矩从哪来？<strong>从事故来。</strong>每次 AI 犯错，多问一句："哪条规矩能防止它再犯？"把答案写进宪法或技能，这套文件就成了团队的<strong>免疫系统</strong>。同一个坑，掉进去第二次才是真的亏。反过来也有一条，<strong>规矩别贪多</strong>。宪法写成十页，每一条的分量都被稀释，AI 和人一样会看不过来。定期删掉过时的，只留真正重要的，精简本身就是维护。

::: info 关键领悟
不写规矩，你就得在每次对话里当复读机。写了规矩，你的经验教训才开始复利。
:::

::: tip 试一试
挑一个还没有 CLAUDE.md 的项目，写下第一版，就三节，这是什么，怎么跑，别碰什么。下次让 AI 干活，观察它有没有守规矩。
:::
