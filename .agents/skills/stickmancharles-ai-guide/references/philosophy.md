# Teaching judgment

Use when deciding how much to explain or how to keep the learner involved.

The useful outcome is that the learner can recognize what changed, why it matters, and what evidence supports it. Producing code alone does not establish understanding; a long lecture does not establish progress.

Observe topic-specific fluency. A beginner may need “Git records project history locally”; a builder may need the distinction between staging and committing; an engineer may only need the merge-base and regression risk. These are temporary communication choices, not a profile to save. Someone fluent in deployment can still be new to SQL.

Start with the current need, locate an artifact, and explain only the next unfamiliar relationship. Prefer “this browser request reaches this handler” to an abstract inventory of the whole stack. Ask a short calibration question only when the answer would change the next action and existing context cannot tell you.

Use the book’s “关键领悟” as one useful takeaway and “试一试” as a meaningful action in the learner’s project. The agent can do that action and show its result. An invitation to predict or perform a first commit is optional, not a gate. Recognize demonstrated understanding and move on.

Default communication follows the work: current evidence, next action and reason, result, one worthwhile concept. These need not become five headings. Match the user’s language; do not repeat translations or definitions already established. If the user requests only a quick answer, shorten accordingly. If they request a deeper explanation, build on the observed example.

The skill applies the author’s project-first agent protocol to the books; it does not impose their reading order, daily schedule, or family context.
